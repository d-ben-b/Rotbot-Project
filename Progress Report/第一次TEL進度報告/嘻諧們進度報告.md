## 1.1 視覺辨識(Ben)

### - 視野

相機的視野要多大才夠用，以及知道要多大之後，怎麼往回推出該買什麼樣的鏡頭跟感光元件。

#### 一、相機必須看到的範圍

我們判斷網板位置的方法是整板 PnP，也就是用一次拍到的多個已知孔中心，反解出整塊網板相對機器人的位置跟角度。這個解法至少要 4 個孔才成立（只有 3 個孔會跑出好幾組無法分辨的解），而且看到的孔越多結果越穩。所以相機必須一次看到 12 個孔，不能只框住等一下要投的那一個。

```
 高度(m)
        +---------------------------------------------+
  2.70  |- - - - - - - - - - - - - - - - - - - - - - -|  <== 視野上界
        |                                             |
  2.60  |      (o)            (o)            (o)      |  加分孔 x3   D=0.20
        |                                             |      | 0.50
  2.10  |     ( O )          ( O )          ( O )     |  主格 R1     D=0.40
        |                                             |      | 0.60
  1.50  |     ( O )          ( O )          ( O )     |  主格 R2
        |                                             |      | 0.60
  0.90  |     ( O )          ( O )          ( O )     |  主格 R3
        |                                             |
  0.70  |- - - - - - - - - - - - - - - - - - - - - - -|  <== 視野下界
        +---------------------------------------------+
                |<--- 0.90 --->|<--- 0.90 --->|
              |<----------- 2.20 m ------------>|
                        （含最外側孔的半徑）
```

圖上的數字是這樣來的：

```
寬   = 0.90 x 2 + 0.40 = 2.20 m   （中心到中心 1.80，左右各再補半個孔徑 0.20）
上界 = 1.50 + 0.60 + 0.50 + 0.10 = 2.70 m
下界 = 1.50 - 0.60 - 0.20        = 0.70 m
高   = 2.70 - 0.70               = 2.00 m
```

相機跟發射口同高（0.40 m），所以換成相機看出去的高度差，是 +0.30 m 到 +2.30 m。

2.50 m 是水平距離，但相機看最上排加分孔是斜著看的，實際距離是 √(2.50² + 2.30²) = 3.40 m。後面算解析度會用 3.40 m。

#### 二、需要多大的視野

視野角就是相機張開的角度。視野越大看得越寬，但同樣數量的像素被攤到更大的範圍，每個像素代表的實際尺寸就越粗，所以視野不是越大越好。

算式：

```
視野角 = 2 x arctan( 要看到的半幅 / 距離 )
```

代入（距離 2.50 m）：

```
水平  HFOV = 2 x arctan(1.10 / 2.50) = 2 x 23.75 = 47.5 度

垂直  看到最高的孔 = arctan(2.30 / 2.50) = 42.6 度
      看到最低的孔 = arctan(0.30 / 2.50) =  6.8 度
      需要的張角   = 42.6 - 6.8          = 35.8 度
```

理論最小值得出，加上誤差算：

| 項目                                        | 量級    | 半幅要多算             |
| ------------------------------------------- | ------- | ---------------------- |
| 基準：12 孔外緣的一半                       | —       | 1.10 m                 |
| 機器人擺位左右偏                            | ±0.15 m | + 0.15 m               |
| 車身朝向沒對正                              | ±3°     | + 2.5 × tan3° = 0.13 m |
| 官方孔位公差                                | ±0.02 m | + 0.02 m               |
| 小計                                        |         | 1.40 m                 |
| 孔不能貼到畫面邊緣（貼邊的孔 PnP 會被排除） | 約 5%   | × 1.05                 |
| 有效半幅                                    |         | **1.47 m**             |

```
HFOV = 2 x arctan(1.47 / 2.50) = 60.9 度  ->  抓 61 度以上
```

> 發射距離目前還沒實測定案，所以依照最壞情況

| 發射距離          | HFOV 理論最小 | HFOV 含餘裕 | 需要垂直張角 | 最遠斜距 |
| ----------------- | ------------- | ----------- | ------------ | -------- |
| 2.0 m（最壞）     | 57.6°         | **71.6°**   | 40.5°        | 3.05 m   |
| 2.5 m（目前估值） | 47.5°         | 60.9°       | 35.8°        | 3.40 m   |
| 3.0 m             | 40.3°         | 53.1°       | 31.8°        | 3.78 m   |

（含餘裕欄是把上面那張表的擺位、車身歪斜、公差、邊緣餘量都算進去的結果。）

#### 三、取捨

> 不讓相機邊瞄準邊定位

目前設計是相機跟槍管同軸，會跟著轉塔一起俯仰。我們用拋體模型把每個孔的投球俯仰角算過一遍：

| 目標             | 視線仰角 | 投球俯仰角 |
| ---------------- | -------- | ---------- |
| 主格最下排       | 10.7°    | 18.4°      |
| 加分孔（最上排） | 41.3°    | 49.5°      |

俯仰角一定比視線高 7 到 9 度，因為球飛出去會往下掉，要抬高一點補回來。

問題就出在這裡：轉塔抬到 49.5° 打加分孔的時候，相機光軸也跟著指到 49.5°，但最低那排孔只在 6.8°，等於掉到光軸下方 42.7°。如果要求「任何瞄準姿態下都看得到整塊板」，垂直視野就得做到 2 × 42.7° = 85.3°。這樣只能上超廣角，畸變大、邊緣精度差，反而減少定位精度。

所以我們改成兩段式：投球前先把轉塔轉到固定的掃視姿態（約 25°）把整塊板框進來完成定位，算出目標角度之後再轉去瞄準投球。這樣垂直視野需求就從 85° 掉到 50° 等級，代價是每次定位多一次轉塔移動。這個機制已經在模擬端做好也驗證過了（`tools/teleop_sim.py` 會自動找出能同時框住 12 個孔的俯仰角）。

#### 四、怎麼從視野推算鏡頭與感光元件規格

推導步驟如下：

```
場地幾何 -> 需要的視野角 -> 焦距(像素) -> 檢查解析度 / 檢查精度 -> 焦距(mm) -> 選鏡頭
```

**步驟 1：視野角換成焦距（以像素計）**

$$
f_{px} = (影像寬度像素 / 2) \div \tan(水平視野 / 2)
$$

這個 $f_{px}$ 就是相機內參，也是我們整套感知唯一相機參數。PnP 解位姿用它，測距公式「距離 = 焦距 × 實際直徑 / 像素直徑」也用它。

**步驟 2：檢查解析度，從最小的特徵反推**

```
物體的像素大小 = 實際尺寸 x f_px / 距離
```

瓶頸是加分孔的紅色 LED 燈條。它是我們判斷「這場哪一格是加分格」的依據。

**步驟 3：檢查精度，比對角解析度與命中容許**

命中容許誤差 =（孔徑 − 球徑）÷ 2：

|        | 容許球心誤差                 | 換算成角度 |
| ------ | ---------------------------- | ---------- |
| 一般孔 | (0.40 − 0.07) ÷ 2 = ±16.5 cm | ±3.78°     |
| 加分孔 | (0.20 − 0.07) ÷ 2 = ±6.5 cm  | ±1.49°     |

感知誤差大概只能吃掉總預算的三分之一，其餘要留給機構背隙跟出射速度變異，所以抓到約 0.5°。

**步驟 4：視野角加上感光元件尺寸，得到實體焦距**

```
焦距(mm)      = (感光元件寬度 mm / 2) / tan(水平視野 / 2)
感光元件寬度  = 水平像素數 x 像素尺寸
```

| 項目                       | 數值                                     | 評估                     |
| -------------------------- | ---------------------------------------- | ------------------------ |
| 視野涵蓋（2.0 m 最壞情況） | 可看到半幅 2.59 m（含餘裕只需 1.44 m）   | 餘裕很大，不可能框不到板 |

結論視野跟精度都過關，要處理的只有亮孔判讀。我們決定沿用原廠鏡頭，軟體端用兩個做法補起來：

1. 板面感知直接用原生解析度推論。板面定位是每投一顆球跑一次，不是即時連續影像，延遲預算以秒計不是毫秒，所以推論可以直接用原生 1920 寬度，燈環就回到 3.1 px。
2. 亮孔判讀改成「幾何定位 + 顏色判別」。整板 PnP 解完位姿之後，三個加分孔投影在畫面上的位置本來就是已知的，直接把那三塊裁出來，在原生解析度下統計紅色飽和像素的比例，最高的就是亮的那格。判斷紅不紅，比辨識一個幾個像素寬的環形穩很多，而且 LED 有 475 lm，鎖定曝光後在畫面上非常明顯。

另外因為原廠鏡頭是超廣角，實機整合有兩件事要注意：畸變標定要用完整的 RATIONAL_MODEL（k1～k6）並且多拍畫面邊角；合成訓練資料要依實測內參重新生成並重訓模型（上次重訓花了約 2.3 小時）。

### - 追蹤高速球體

為什麼相機一定要用全域快門（global shutter），以及如果改用一般的捲簾快門（rolling shutter），軟體端要額外付出多少代價。

#### 一、我們為什麼要追球

追球的目的是支撐線上校正，整套得分策略都建立在這上面。

機器人腦內的瞄準模型是刻意簡化過的，忽略空氣阻力；實際上飛輪會打滑、機構有安裝偏差、每一發的初速也會抖。所以第一球幾乎不可能準。我們的作法是每投一球就用相機量落點，把誤差回饋回去修下一球的角度，投個幾球就把手感找回來。

模擬跑出來的差別很大（60 場蒙地卡羅，模擬評估）：

|              | 沒有校正 | 有校正   |
| ------------ | -------- | -------- |
| 總分         | 43.2     | **51.0** |
| 命中率       | 80%      | **91%**  |
| 加分孔命中率 | 1%       | **27%**  |

加分孔那一欄最明顯，因為它只有 Ø20 cm，容許誤差只有 ±6.5 cm，沒有校正基本上投不進。而校正大約要 4 到 6 球才收斂——一場只有 27 顆球，加分孔又只有開賽前 60 秒會亮，所以**每一球的落點都必須量到，不能浪費**。

結論是：落點量測是拿分的前提，而落點量測就是在拍一顆飛行中的球。

#### 二、落點要量到多準

用 v0 = 9.6 m/s（出射速度實測估值）算：

| 目標     | 投球俯仰 | 飛行時間 | 球到板面時離相機 |
| -------- | -------- | -------- | ---------------- |
| 主格中排 | 32.0°    | 307 ms   | 2.58 m           |
| 加分孔   | 50.4°    | 408 ms   | 3.15 m           |

在 2.5 m 處，原廠鏡頭的 1 個像素代表 0.34 cm。換算過去：

```
一般孔容許 ±16.5 cm = ±49 px
加分孔容許 ±6.5 cm  = ±19 px
校正演算法的量測雜訊預算（meas_noise_m） = 2 cm = 6 px
```

也就是說，落點量測的誤差必須壓在 **2 cm** 等級，否則餵給校正的資訊本身就不可靠。

#### 三、捲簾快門的缺點

相機跟槍管同軸，球幾乎是沿著光軸飛出去的，在畫面上的橫向速度只有 350 到 380 px/s。曝光開 1/1000 秒，運動模糊只有 0.4 px，等於沒有模糊。這一項我們過得去。

真正的問題是**時間**。捲簾快門不是整張圖同一瞬間曝光，而是一行一行掃下來，整張掃完大約要 16 ms（60 fps 的量級）。所以「球出現在畫面第幾行」會決定它實際上是哪個時刻被拍到的。

把數字代進去：

| 球的位置 | 影像速度 | 捲簾造成的位置偏差（readout 16 ms） |
| -------- | -------- | ----------------------------------- |
| 飛行中點 | 350 px/s | 6 px = 1.1 cm                       |
| 接近板面 | 379 px/s | 6 px = **2.1 cm**                   |

2.1 cm 剛好把我們 2 cm 的量測預算整個佔據。但更麻煩的不是大小，是它的性質：

**這是跟球在畫面位置相關的系統性偏差，不是隨機雜訊。** 校正演算法的設計就是用來吸收系統性偏差的——穩健度實驗顯示，把安裝偏差放大兩倍，校正能把命中率從 19% 拉回 91%。同樣的機制下，捲簾造成的偏差也會被當成機構偏差一起修正，等於往錯的方向調。隨機雜訊的影響反而比較小，多投幾球就平均掉了。

另外還有一個連帶效應：為了避免模糊要壓短曝光，進光量變少就得拉高增益，雜訊上升。而曝光是整台相機的全域設定，動了它就會同時影響亮孔的紅色判讀，那邊要重新驗證一次。

#### 四、如果不用全域快門，程式要多做什麼

用捲簾快門的話，上面的時間問題不會自己消失，得在軟體裡補回來：

| 工作項目           | 要做什麼                                                                                           | 估計工時       |
| ------------------ | -------------------------------------------------------------------------------------------------- | -------------- |
| readout 時間標定   | 規格書通常不寫，要自己量（拍旋轉標的或掃描式 LED），還要確認 frame timestamp 對應到第幾行          | 2～3 天        |
| 逐行時間戳模型     | 偵測到球之後，真正時刻 = frame 時戳 + (第幾行 / 總行數) × readout 時間，後面所有計算都要吃這個修正 | 1～2 天        |
| 多幀關聯與軌跡擬合 | 從「拍一張量位置」變成「連續多幀、每幀各自的時間戳、擬合拋物線再外推板面交點」                     | 3～5 天        |
| 曝光策略重調       | 壓短曝光、補增益、重新驗證亮孔紅色判讀不受影響                                                     | 2～3 天        |
| 驗證方案           | 沒有真值可比對，要另外搭一套（固定落點靶紙或高速攝影對照）                                         | 3～5 天        |
| 合計               |                                                                                                    | **約 2～3 週** |

乾脆放棄量連續落點，改成只判斷「這球有沒有進」的二元回饋。但這樣校正就從「知道差多少、該往哪修」退化成「只知道沒中」，收斂需要的球數會遠超過我們手上的 27 顆，等於回到上面那張表的「沒有校正」那一欄。

#### 五、選用相機的驗算

**e-CAM25_CUONX** 用的 AR0234CS 本身就是全域快門，所以上面整節的問題在買相機的當下就解決了，軟體端一行都不用補。順便驗算追蹤能力：

| 項目                 | 數值                   | 評估                             |
| -------------------- | ---------------------- | -------------------------------- |
| 幀率                 | 2.3MP@60fps，HD@120fps | 夠                               |
| 球到板面時的大小     | 16～20 px              | 夠偵測                           |
| 幀間位移（60 fps）   | 6.3 px，約 0.3 顆球徑  | 位移遠小於球徑，連續幀不會配錯球 |
| 幀間位移（120 fps）  | 3.2 px，約 0.16 顆球徑 | 更穩                             |
| 運動模糊（1/1000 s） | 0.4 px                 | 幾乎沒有                         |
| 時間戳               | 整張同一時刻           | 落點量測直接對得上 2 cm 的預算   |

要補充的是，AR0234 的全域快門是為了追球買的，但它同時也讓板面定位受益：轉塔剛轉到掃視姿態、機構還有殘餘晃動時拍的那張，捲簾會把整塊網板拍歪，全域快門不會。

### - 圖形映射與位置計算

從一張影像怎麼算出「轉塔要轉幾度」，以及 PnP 這條路上我們遇到的問題。

#### 一、整條鏈路

```
相機影像
   |
   |  YOLO 偵測：每個孔的中心像素 + bbox + 類別（一般孔 / 加分孔 / 亮起的加分孔）
   v
孔中心像素
   |
   |  孔編號對應：把偵測到的圓對到「第幾號孔」（見下節第 4 項）
   v
偵測 <-> 已知孔中心 的配對
   |
   |  整板 PnP：12 個已知的 3D 孔中心 + 對應像素 -> 解出整塊網板的位置與角度
   v
網板位姿 (R, t)
   |
   |  逐孔幾何：算出每個孔的 (距離, 方位角, 俯仰角)，此時還是相機座標系
   v
相機系的孔位置
   |
   |  座標轉換：軸置換 + 相機相對槍口的外參（rotbot/decision/frames.py）
   v
發射點座標系的 3D 目標
   |
   |  拋體反解（rotbot/decision/ballistics.py）
   v
轉塔要轉的 (俯仰角, 水平角)
```

這裡最關鍵的設計決定是：**中間一定要經過「整塊板的位姿」，不是直接對每個孔各自測距。**

因為整板 PnP 是拿 12 個點去過定求解一組解，單一個孔的偵測誤差會被其他 11 個平均掉；逐孔測距則是每個孔各自為政，誤差直接進到結果裡。差距在模擬裡很明顯：

| 方法           | 距離誤差                | 方位/俯仰誤差 | 能不能給孔的傾角    | 定位                        |
| -------------- | ----------------------- | ------------- | ------------------- | --------------------------- |
| 整板 PnP       | 0.2～0.5 cm             | 約 0.06°      | 不能                | **主力**（需要至少 4 個孔） |
| 表觀直徑測距   | 約 6 cm，而且是系統性的 | —             | 不能                | 孔數不足 4 個時的備援       |
| 橢圓圓錐反投影 | 0～2 cm                 | 約 0.08°      | **能**（0.6～1.8°） | 補單孔傾角用                |

（60 場、有注入偵測雜訊的模擬比較。）

#### 二、開發過程中的幾次修正

這條鏈路改過幾次，以下依時間順序記錄每一次遇到的狀況、原因跟處理方式。

**1. 目標形狀由正方形改為圓孔**

最早的原型用的是 `SOLVEPNP_IPPE_SQUARE`，假設目標是正方形、要餵四個角點，YOLO 也是照關鍵點偵測的方向在準備。後來對照官方工程圖確認，九宮格是**圓孔**（一般 Ø40 cm、加分 Ø20 cm）。

圓沒有角點，原本的方案前提不成立。原型的模擬在這一點上本身也不一致——校正模擬把那個數字當直徑用，PnP 卻當成邊長用。

處理方式是全面改成「圓孔中心 + 整板 PnP」，`config` / `scene` / `detector` / 資料集工具 / `pose` 全部重寫，YOLO 也從關鍵點改成一般的 bbox 偵測（圓孔中心定義清楚，bbox 就夠用，標註更省、在 Orin 上也更快）。同時把孔的座標佈局集中到同一份設定（`Config.hole_centers()`），讓感知跟模擬共用同一份幾何。

**2. 共面點的位姿求解不穩定**

改成圓孔之後，第一版用 `solvePnPRansac` 解位姿，50 場裡會失敗 6 場。原因是 12 個孔全部落在同一個平面上，RANSAC 在共面點上本來就不穩定。改用平面專用的解法（IPPE）之後穩定下來。

**3. 正對網板時 IPPE 會退化**

接著遇到比較隱晦的狀況：機器人剛好正對網板的時候（fronto-parallel），IPPE 會退化，解出來的角度跳動很大。而正對正好是我們最常出現的姿態。

改用 SQPNP 之後解決，指標改善幅度如下：

|                    | 改之前（IPPE） | 改之後（SQPNP） |
| ------------------ | -------------- | --------------- |
| 整板 PnP 成功      | 45 / 50        | 46 / 50         |
| 距離誤差平均       | 8.3 cm         | **4.9 cm**      |
| 距離誤差 95 百分位 | 27.2 cm        | **16.4 cm**     |
| 方位誤差 95 百分位 | 12.9°          | **1.19°**       |

**4. 孔的編號指派錯誤，導致個別孔瞄準偏差過大（95 百分位 114 cm）**

這一項最難定位。位姿解得出來、數值看起來也正常，但個別孔算出來的瞄準點偶爾會差很多。

原因出在「這個偵測到的圓是第幾號孔」這一步，原本是用 2D 行列分群指派的——把偵測結果按 y 座標分三排、再按 x 座標分三欄。這在乾淨的合成影像上沒問題，但真實偵測會有多餘的框、被畫面切掉的邊緣孔、偶爾的誤分類，只要多一個框整排編號就會錯位，每個孔都拿到別人的座標。

改成**投影重匹配**：先用初估的位姿把已知的孔中心投影回影像，再讓每個偵測就近認領離自己最近的那個編號，最後用修正後的對應重解一次位姿。認領設有門檻（投影後孔與孔之間最近距離的一半），避免配到不相干的孔。

**5. 被畫面邊緣切到的孔**

孔如果只有一半在畫面裡，bbox 的中心會往內偏，這個偏差會直接影響 PnP。處理方式是求解時把碰到畫面邊緣的偵測排除，只拿來顯示、不參與定位。

前面「視野」那節多留的 5% 邊緣餘裕就是為了這件事。

**6. bbox 中心與透視圓心的落差（目前殘留誤差的主因）**

圓在透視投影下會變成橢圓，而**橢圓的中心並不等於圓心的投影位置**，斜看的時候差距更明顯。目前拿 bbox 中心當孔中心用，本身就帶有一個系統性偏差。

這一項目前維持現狀，原因是 4.5 cm 的誤差還在一般孔 ±16.5 cm 的容許範圍內，而且屬於系統性偏差，線上校正吸收得掉。需要更高精度時再改用橢圓擬合的中心，同時還能取得孔的傾角（網板被打歪時會用到）。

#### 三、目前的精度

用訓練好的 YOLO 跑端到端評估（50 場合成場景，**模擬評估、非實機成績**）：

| 項目                 | 數值    |
| -------------------- | ------- |
| 整板 PnP 成功        | 44 / 50 |
| 亮起的加分孔正確帶出 | 8 / 8   |
| 距離誤差平均         | 4.5 cm  |
| 方位誤差             | 1.47°   |
| 俯仰誤差             | 0.55°   |

對照命中容許（一般孔 ±16.5 cm、加分孔 ±6.5 cm），一般孔的餘裕很夠；加分孔的方位誤差已經貼近容許值，這也是為什麼線上校正對加分孔特別重要——模擬裡加分孔命中率從 1% 拉到 27%，靠的就是校正。

#### 四、還沒解決的

| --------------------- | ------------------------------------------------------------- | ----------------------------------------------------- |
